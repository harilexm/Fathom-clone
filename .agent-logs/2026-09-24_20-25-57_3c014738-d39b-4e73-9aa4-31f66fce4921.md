### 1. Direct Browser → R2 Upload

#### Concrete Issue 1.1: `Content-Type` Header Mismatch Triggers `403 Forbidden` (`SignatureDoesNotMatch`)
* **Location**: [src/components/my-calls.tsx](file:///c:/Users/DeLL/Desktop/SidePROJECTs/FathomClone/src/components/my-calls.tsx#L80-L106) & [src/lib/r2.ts](file:///c:/Users/DeLL/Desktop/SidePROJECTs/FathomClone/src/lib/r2.ts#L172-L176)
* **Problem**: In `my-calls.tsx` (line 81), requesting the presigned URL passes:
  ```typescript
  contentType: file.type || "video/mp4"
  ```
  If the browser cannot detect the MIME type (which frequently happens on Windows and macOS for `.mov`, `.mkv`, or `.m4a` files where `file.type === ""`), the presigned URL endpoint signs the request expecting `Content-Type: video/mp4` in `x-amz-signedheaders`.  
  However, in the XHR upload (line 103), the header is set conditionally:
  ```typescript
  if (file.type) {
    xhr.setRequestHeader("Content-Type", file.type);
  }
  ```
  Because `file.type` was empty, the browser omits the `Content-Type` header (or sends `application/octet-stream`), causing Cloudflare R2 to reject the upload with **`403 Forbidden (SignatureDoesNotMatch)`**.
* **Solution**: Ensure the exact same content type is sent in both requests:
  ```typescript
  const effectiveContentType = file.type || "video/mp4";
  // Send effectiveContentType to /api/recordings/upload-url AND:
  xhr.setRequestHeader("Content-Type", effectiveContentType);
  ```
  *(Alternatively, omit `ContentType` from the presigned URL's `PutObjectCommand` so AWS SigV4 does not bind the signature to a specific `Content-Type` header).*
